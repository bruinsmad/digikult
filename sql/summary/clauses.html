2One query, every clause

You rarely need all seven clauses at once, but when you do, they always come in this order:

SELECT genre, COUNT(*)what to show: columns or calculated values
FROM bandswhich table (or tables) to read
WHERE members >= 2which rows to keep
GROUP BY genrewhich rows go into one group
HAVING COUNT(*) >= 2which groups to keep
ORDER BY COUNT(*) DESCin what order the result comes
LIMIT 3;at most how many rows to show

4What the database really does

You start writing with SELECT, but the database works in a different order:

  1. FROMtakes the table (with several tables, it pairs up rows first)
  2. WHEREthrows out the rows you don't need
  3. GROUP BYputs the remaining rows into groups
  4. HAVINGthrows out the groups you don't need
  5. SELECTworks out the columns and values you asked for
  6. ORDER BYsorts the result
  7. LIMITcuts off the rest
💡

That's why COUNT or SUM can't go in WHERE: when WHERE runs, there are no groups yet to count. HAVING comes after grouping, so there it's allowed.

8Joining several tables

List the tables after FROM, separated by commas, and put the matching rule in WHERE: the referring number equals the other table's id.

SELECT bands.name, concerts.day
FROM concerts, bands
WHERE concerts.band_id = bands.id;
  • If a column name is in both tables, write the table name in front of it: bands.name.
  • Without the rule, every row pairs with every row (12 × 8 = 96 rows).
  • Two tables need one rule, three tables need two, joined with AND.
  • After the rule, everything else still works: more conditions, GROUP BY, ORDER BY.

9Common mistakes

✗ Wrong
SELECT name FROM bands
WHERE genre = folk;
✓ Right
SELECT name FROM bands
WHERE genre = 'folk';

Without quotes, SQL thinks folk is a column name: no such column: folk.

✗ Wrong
SELECT day FROM concerts
WHERE SUM(audience) > 3000
GROUP BY day;
✓ Right
SELECT day FROM concerts
GROUP BY day
HAVING SUM(audience) > 3000;

An aggregate function can't go in WHERE. Groups are filtered with HAVING.

✗ Wrong
SELECT name FROM bands
ORDER BY members DESC
WHERE members > 2;
✓ Right
SELECT name FROM bands
WHERE members > 2
ORDER BY members DESC;

The order of the clauses is fixed: WHERE always comes before ORDER BY.

✗ Wrong
SELECT bands.name, concerts.day
FROM concerts, bands;
✓ Right
SELECT bands.name, concerts.day
FROM concerts, bands
WHERE concerts.band_id = bands.id;

Without the matching rule you get 96 rows, most of them pairs that don't belong together.

✗ Wrong
SELECT name FROM bands
WHERE country = NULL;
✓ Right
SELECT name FROM bands
WHERE country IS NULL;

= NULL is never true, so you get 0 rows and no error message.

10Check yourself

Which clause filters groups?

WHERE filters rows before grouping, HAVING filters groups after it.

What's wrong with this query?
SELECT name FROM bands
ORDER BY members
WHERE members > 3;

The order is SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT.

How many rows does this give?
SELECT day, COUNT(*)
FROM concerts
GROUP BY day;

Each group becomes one row, and there are three different days: Friday, Saturday and Sunday.

What do you get?
SELECT * FROM concerts
ORDER BY audience DESC
LIMIT 1;

DESC puts the largest first, and LIMIT 1 keeps only that one.

You join three tables. How many matching rules do you need?

One for each link: three tables are held together by two links.
