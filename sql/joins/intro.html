Joining tables

In a good database every piece of data lives in exactly one place, and tables refer to each other with numbers. When a question needs several tables, you list them after FROM and say in WHERE which row belongs to which.

2Why just a number?

concerts doesn't store the band's name, only its id, in the band_id column. That's a reference: band_id = 2 means "the band whose id is 2".

concerts.band_id → bands.id
concerts.stage_id → stages.id
  • Every name is in one place: if a band changes its name, you fix one row.
  • No repetition and no typos: both Paprika Punks concerts point to the same row.

By hand, you'd find out who plays on Saturday at 22:00 like this: read the number first, then look up the name that goes with it.

3Two tables after FROM: every row with every row

When you write two tables after FROM, SQL pairs every row of the first with every row of the second. 6 concerts × 4 bands = 24 pairs, and most of them are nonsense (like a Velvet Locomotive concert with the Paprika Punks' name).

4The matching rule

A concert belongs to a band when the concert's band_id equals the band's id. That's what you write in WHERE:

WHERE concerts.band_id = bands.id

Both tables have an id column, so you must write the table name in front of it, or SQL won't know which one you mean. The easiest habit: always write it, like concerts.day, bands.name.

7Kinds of links

kindmeaningexample
N : 1many rows can point to the same rowmany concerts → one band (band_id can repeat)
1 : 1every row has exactly one partnerevery band has exactly one manager
N : Nmany on both sidesa band plays on several stages, a stage hosts several bands: the concerts table links them
💡

An N : N link is always stored in a third, “linking” table. Here that's concerts: each row is one band–stage pair.

8Common mistakes

✗ Wrong
SELECT bands.name, concerts.day
FROM concerts, bands
WHERE bands.name = 'Paprika Punks';
✓ Right
SELECT bands.name, concerts.day
FROM concerts, bands
WHERE concerts.band_id = bands.id
  AND bands.name = 'Paprika Punks';

Without the rule all 6 concerts get paired with Paprika Punks. The right answer is 2 concerts.

✗ Wrong
SELECT bands.name, concerts.day
FROM concerts, bands
WHERE concerts.id = bands.id;
✓ Right
SELECT bands.name, concerts.day
FROM concerts, bands
WHERE concerts.band_id = bands.id;

concerts.id is the concert's number, not the band's. The matches are coincidences: 4 rows of wrong pairs.

✗ Wrong
SELECT id, name, day
FROM concerts, bands
WHERE band_id = bands.id;
✓ Right
SELECT concerts.id, bands.name, concerts.day
FROM concerts, bands
WHERE concerts.band_id = bands.id;

id is in both tables: ambiguous column name: id. Write the table name in front of it.

✗ Wrong
SELECT bands.name, stages.name
FROM concerts, bands, stages
WHERE concerts.band_id = bands.id;
✓ Right
SELECT bands.name, stages.name
FROM concerts, bands, stages
WHERE concerts.band_id = bands.id
  AND concerts.stage_id = stages.id;

Three tables need two rules. With only one, every concert is paired with both stages: 12 rows instead of 6.

9Check yourself

How many rows does this query return?
SELECT *
FROM concerts, bands;

Without WHERE every row is paired with every row: 6 × 4 = 24.

Which is the right matching rule?

The referring column (band_id) equals the id of the table it refers to.

How many matching rules do you need with three tables after FROM?

n tables need n − 1 rules: three need two.

Why write bands.id instead of just id?

When a column name appears in several tables, the table name says which one you mean.
